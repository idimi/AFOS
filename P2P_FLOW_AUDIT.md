# P2P Swap Flow Audit — Root Cause Analysis

## The Intended Flow (what SHOULD happen)

```
Agent A (Taker)                    Signaling Server           Agent B (LP/Maker)
─────────────────────────────────────────────────────────────────────────────────
1. "swap 0.01 SOL to USDT"
2. Server finds B in signaling registry
3. Server sends agent_rfq to B ──────────────────────────────> B receives agent_rfq
4. A gets quote_card with P2P badge                            B shows incoming swap card
5. A clicks "Confirm Swap"
6. A initiates HTLC lock (signs tx)
7. A sends htlc_locked msg ──────────────────────────────────> B receives htlc_locked
8.                                                             B initiates HTLC lock (signs tx)
9.                                                             B sends htlc_locked msg <──────
10. A receives B's htlc_locked
11. A reveals secret hash
12. B claims with secret ──────────────────────────────────── Settlement complete
13. Both sides update "Recent Swaps"
```

## What ACTUALLY happens (broken)

### Bug 1: Agent A's "Confirm Swap" does NOTHING for P2P
- `handleConfirmSwap` in ChatPage.tsx calls `buildSwapTx.mutateAsync()`
- `buildSwapTx` returns `{ route: "AFOS P2P", p2pQuote }` 
- ChatPage sees `solResult.route === "AFOS P2P"` and just shows a toast "P2P peer matched!"
- **NO HTLC is initiated. NO message is sent to Agent B. Nothing happens.**
- Agent A's UI shows "Confirm Swap" card forever with no state change.

### Bug 2: Agent B's "Accept" does NOT notify Agent A
- Agent B clicks Accept in the chat page → calls `handleSend("accept swap ... rfq:xxx")`
- Server's `sendMessage` handler matches `acceptMatch` regex → returns a text message
- **NO signaling message is sent to Agent A. Agent A never knows B accepted.**
- Agent B's `acceptRfq()` in LightPeerContext calls `submitQuote()` (posts to Oracle VM)
  but the Oracle VM `/api/rfq/:id/quote` endpoint just stores the quote for the order book.
  **It does NOT send any message back to Agent A.**

### Bug 3: The HTLC modal is 100% mock
- `acceptRfq()` in LightPeerContext calls `setHtlcSigning({ step: "locking" })`
- If no wallet is connected: waits 1 second, then `setHtlcSigning({ step: "settled" })`
- **No actual blockchain transaction is attempted. No real HTLC is created.**
- The modal shows all 4 steps checked ✓ instantly — it's purely cosmetic.

### Bug 4: The "Connect Wallet to Swap" button on Agent A's quote card
- Agent A's chat shows a quote card with "Connect Wallet to Swap" even though wallet IS connected
- This is because the quote card checks `quoteData.fromChain` but the P2P route doesn't
  properly set the wallet connection state for the button label.

### Bug 5: No bidirectional HTLC coordination
- There is NO mechanism for Agent A and Agent B to exchange HTLC parameters:
  - Secret hash (generated by one side, shared with the other)
  - Lock transaction hashes (so both sides can verify on-chain)
  - Timelock values (must be coordinated: A's timelock > B's timelock)
- The signaling server has `peer_message` for direct peer-to-peer messages but
  **it is never used for HTLC coordination**.

### Bug 6: Recent Swaps never updates for P2P
- `recordSwapAnalytic` is called in `buildSwapTx` with `status: "completed"` BEFORE
  the HTLC is even initiated — this is premature and incorrect.
- After a real swap, neither Agent A nor Agent B has code to record the swap completion.

## The Fix Plan

### New P2P State Machine
States: `idle` → `rfq_sent` → `quote_received` → `htlc_initiating` → `htlc_locked_a` → `htlc_locked_both` → `settling` → `complete` | `failed` | `refunded`

### New Signaling Messages (bidirectional)
- `p2p_quote_accepted` — B → A: "I accept your RFQ, here are my wallet addresses"
- `p2p_htlc_params` — A → B: "Here is the secret hash, timelock, my lock tx hash"
- `p2p_htlc_locked` — B → A: "I have locked my side, here is my lock tx hash"
- `p2p_swap_complete` — A → B: "Secret revealed, swap complete"
- `p2p_swap_failed` — either direction: "Something went wrong, refund your HTLC"

### Rewrite Scope
1. **server/signaling.ts** — add new message types, store in-flight swap state
2. **server/routers/chat.ts** — `buildSwapTx` must send `p2p_htlc_params` to B after A locks
3. **client/src/contexts/LightPeerContext.tsx** — rewrite `acceptRfq` to:
   - Send `p2p_quote_accepted` to A via signaling
   - Wait for A's `p2p_htlc_params`
   - Initiate B's HTLC lock
   - Send `p2p_htlc_locked` to A
4. **client/src/pages/ChatPage.tsx** — rewrite `handleConfirmSwap` for P2P to:
   - Wait for B's `p2p_quote_accepted` message
   - Initiate A's HTLC lock
   - Send `p2p_htlc_params` (secret hash + timelock + lock tx) to B
   - Wait for B's `p2p_htlc_locked`
   - Reveal secret to complete swap
5. **client/src/pages/Swaps.tsx** — same HTLC flow for order book accept path
6. **Swap completion** — record to DB only after both sides confirm locked

## Key Design Decisions

1. **Secret generation**: Agent A (taker) generates the secret. This is standard HTLC protocol.
2. **Timelock**: A's timelock = 2 hours, B's timelock = 1 hour (B's must expire first so A can't steal)
3. **For demo/testnet**: If wallet signing fails, show clear error instead of fake "settled" state
4. **Cross-chain**: Same protocol, different chains. B locks on their chain, A locks on their chain.
5. **No Oracle VM dependency**: The HTLC coordination happens purely via signaling WebSocket.
   Oracle VM is only used for the order book (quote broadcasting).
